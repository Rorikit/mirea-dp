# Обзор проекта

## Цель и границы MVP

Система обслуживает «День первокурсника РТУ МИРЭА» 1 сентября 2026 года (часовой пояс `Europe/Moscow`): импортирует утверждённый список, регистрирует студента по точному нормализованному совпадению ФИО и группы, выдаёт одноразовый QR, фиксирует входы/выходы, показывает карту и расписание, предоставляет операторские и административные функции.

MVP — адаптивное одностраничное веб-приложение. Архитектура — модульный монолит: один backend API, один frontend с ролевыми маршрутами, PostgreSQL и Nginx. Бизнес-логика, настоящий импорт, QR, авторизация, статистика и контент карты/расписания в текущий каркас намеренно не входят.

## Заинтересованные стороны и успех

Студенту нужен быстрый безопасный вход; оператору — надёжное сканирование со смартфона; администратору — контролируемый импорт и наблюдаемость; университету — сохранность персональных данных и полный журнал. Успех: ни одного двойного события от одного QR, импорт атомарен, критические ошибки блокируют подтверждение, права проверяются backend, история не теряется.

## Противоречия и решения

| Вопрос | Решение MVP |
|---|---|
| QR «одноразовый», но нужен повторный вход | Каждый токен одноразовый; после выхода новый ENTRY-токен выдаётся только по кнопке студента. |
| Импорт C деактивирует отсутствующих, но файл может быть неполным | Полная синхронизация только с отдельным явным подтверждением числа деактиваций; порог аномалии требует контрольной фразы. |
| Регистрация названа публичной, но нужен «свой кабинет» | После регистрации выдаётся непрозрачная защищённая cookie-сессия студента; поиск сам по себе сессию не создаёт. |
| `READY_TO_CONFIRM`, `CONFIRMED`, `APPLIED` | `CONFIRMED` — краткое зафиксированное намерение внутри операции подтверждения; успешный commit даёт `APPLIED`, rollback — `FAILED`. |
| Один или два frontend | Один React-проект: публичная и защищённые операторская/административная области. |
| Карта предполагает `MapZone`, но MVP минимален | Растровое WebP/PNG-изображение без интерактивных зон; `MapZone` зарезервирован. |
| «Сброс статистики» против неизменяемой истории | Физического сброса нет; архивируется Event и создаётся новый. |

## Допущения

- Один развёрнутый экземпляр может хранить несколько мероприятий; все предметные данные изолированы `event_id`.
- Максимум файла: 20 MiB и 50 000 строк; первый непустой лист, одна строка заголовков; дополнительные колонки игнорируются с предупреждением.
- `source_id` — строка до 128 символов после обрезки пробелов, регистр и ведущие нули значимы.
- Срок QR — 15 минут; серверное время синхронизируется NTP.
- Операторская/административная аутентификация — короткий access token в памяти клиента и rotating refresh token в `HttpOnly Secure SameSite=Strict` cookie.
- Срок хранения ПДн и аудит юридически уточняется; до решения данные не удаляются автоматически.

## Открытые вопросы

1. Кто владелец и оператор ПДн, каковы основание обработки, сроки хранения и процедура обращений субъектов?
2. Каков ожидаемый размер базы, число одновременных студентов/операторов и целевой SLA?
3. Уникален ли исходный `id` только внутри мероприятия или глобально?
4. Подтверждены ли правила написания групп и эквивалентность `ё/е` владельцем данных?
5. Нужны ли несколько КПП, офлайн-режим сканера и ручная коррекция посещений?
6. Кто может активировать мероприятие и утверждать массовую деактивацию?
7. Допустимо ли оператору видеть полные ФИО; нужен ли маскированный режим?
8. Какой официальный брендбук и исходник карты предоставляются?
